Apple HIG Foundation

Native, adaptive, privacy-safe UI for HIGDesign.

This library converts the Apple Human Interface Guidelines map into HIGDesign-specific design rules, tokens, patterns, and SwiftUI implementation notes for iOS, iPadOS, macOS, visionOS, tvOS, and watchOS.

Operating Rules

Design principles

These rules are the baseline for all HIGDesign public API work. They are intentionally stricter than a loose visual style guide because components must stay token-driven, theme-driven, and Apple-native.

Native first

Use SwiftUI controls and platform patterns before custom UI. Custom controls need a workflow, accessibility, and platform justification.

MandatorySwiftUI

Adaptive by default

Design for all six Apple platforms. Prefer native layout conventions per idiom instead of one fixed phone layout stretched everywhere.

iOSiPadOSmacOSvisionOStvOSwatchOS

Tokens own visuals

Components render from raw, semantic, and component tokens resolved through HIGTheme. Application business logic stays outside the design-system package.

ArchitectureHIGTheme

Privacy in every surface

Do not log user-entered text, secrets, private app content, or implementation internals from library diagnostics.

PrivacyLogging

Design Tokens

HIGDesign system tokens

Use system-adaptive color, type, spacing, and materials. These tokens are descriptions for SwiftUI implementation, not hard-coded app colors.

Accent

Use system accent for primary actions, selection, and current navigation.

Success

Use sparingly for completed states, approved content, and valid outcomes.

Attention

Use for pending review, warnings, and moderation attention states.

Destructive

Use for destructive actions, rejected states, and critical validation.

Grouped surface

Map to grouped backgrounds, materials, and list surfaces rather than flat custom fills.

Separator

Use system separators and dividers for hierarchy. Avoid decorative borders.

Getting Started

Platform model

HIGDesign uses one Apple-native product system with platform-specific presentation. The same feature can have different navigation density by device.

iPhone

Use tab-based top-level navigation, stack-based detail flows, full-screen or large sheets for complex forms, and visible primary actions.

iPad

Components

Reusable component rules

These are implementation defaults for `HIGComponents`. Add reusable components only when they reduce repeated real complexity across consuming apps.

Buttons and menus

Use text for clear commands, SF Symbols for familiar tool actions, menus for grouped secondary actions, and confirmation for destructive work.

Lists and tables

Use `HIGList` for grouped content and row actions. Use native table patterns on macOS when dense comparison is required.

Sheets and popovers

Sheets are for bounded tasks. Popovers are for lightweight choices. Complex editors need larger presentation or window-based workflows.

Progress and feedback

Async work needs clear loading, disabled in-flight controls where needed, success feedback when it matters, and actionable error recovery.

Inputs

Keyboard, pointer, and gesture rules

HIGDesign components must work beyond touch-only interaction on Mac, iPad, TV, and visionOS.

  • OKText-heavy editors should support keyboard focus, selection, and predictable submit/cancel actions.
  • OKPointer hover can reveal secondary affordances, but required actions must stay discoverable without hover.
  • OKGestures should supplement visible controls, not replace them for core or destructive actions.
  • OKmacOS components should consider keyboard shortcuts only when visible menu or toolbar commands also exist.

Technologies

Out of package scope

HIGDesign documents HIG-aligned component behavior only. Application technologies such as CloudKit, StoreKit, Sign in with Apple, widgets, and push notifications belong in consuming apps, not in the core package.

Consuming app integrations

Apps may compose HIGDesign components inside their own feature, sync, purchase, and account flows.

Showcase examples

Showcase may demonstrate composition patterns without importing application-only SDKs into library targets.

Bridging layer

Optional `HIGBridging` may wrap Cocoa controls for SwiftUI gaps while still styling them with HIG tokens.

Platform services

Permission, account, and commerce UI should use system patterns in app code rather than design-system components.

PR Readiness

HIG checklist summary

Paste this shape into PR bodies for user-facing UI work and fill it with specific notes.

  • OKHIG sections reviewed: foundations, patterns, components, inputs, technologies.
  • OKNative SwiftUI components used, or custom UI justification provided.
  • OKNavigation and layout behavior fits every targeted platform.
  • OKSheet, popover, inspector, or window sizing is appropriate for workflow complexity.
  • OKEmpty, loading, error, disabled, and success states are accounted for.
  • OKAccessibility labels, Dynamic Type, contrast, keyboard, and pointer behavior are considered.
  • OKLogging avoids user-entered text, secrets, and private app content.
  • OKApplication business logic remains outside design-system components and modifiers.
